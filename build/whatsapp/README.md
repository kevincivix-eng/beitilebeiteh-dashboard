# מסלול ניסוי: נתוני מסירות מקבוצות הוואטסאפ

חילוץ נתוני מסירות מתמלולי קבוצות הוואטסאפ. הפלט נכתב ל-`data/whatsapp/`
ומשולב לדשבורד החי בזמן הבילד.

## איך זה מגיע לדשבורד

`build/merge_whatsapp.js` מחבר את התוצרים לנתוני Airtable **בתוך** `fetch_data.js`.
זה קריטי: `data/*.json` נבנים מחדש בכל הרצת CI (קרון יומי), ולכן עריכה ישירה של
הקבצים הייתה נמחקת בפריסה הבאה. המיזוג בזמן בילד הוא מה שמשמר את הנתונים.

שני המקורות מתארים את **אותה פעילות בתקופות שונות** (Airtable עד מאי 2026, וואטסאפ
מיוני 2026), ולכן הם מסוכמים למספר אחד — הדשבורד מציג רצף אחד, לא "ישן" ו"חדש".

המיזוג אידמפוטנטי: כל הרצה מתחילה מנתוני Airtable טריים, אז הרצה חוזרת לא מכפילה.

## גבולות בטיחות

- **לא נוגע ב-Airtable** מלבד קריאה אחת של קטלוג `רשימת חפצים`. אין בקוד הזה שום `POST`/`PATCH`/`DELETE`.
- **מסתיר מספרי טלפון** בכל קובץ פלט (`[טלפון]`). תיקיית `whatsapp/` מוחרגת מ-git — היא מכילה ~3.8GB מדיה ומידע אישי.
- **נקודת שחזור:** התג `restore-point-v0.3.3` מצביע על הגרסה החיה לפני השילוב.

## הרצה

```bash
# 1. מטמון הקטלוג (פעם אחת; קריאה בלבד מ-Airtable)
AIRTABLE_API_KEY=pat... node build/whatsapp/fetch-catalog.js

# 2. פירוק התמלולים + איחוד כפילויות בין הקבוצות
node build/whatsapp/parse.js

# 3. חילוץ עיר + פריטים (לקסיקון)
node build/whatsapp/extract.js

# 4. העשרה במשקלים + אגרגציה
node build/whatsapp/build-exp.js
```

ואז לפתוח את `exp.html` דרך שרת מקומי.

## איך עובד איחוד הכפילויות

אותו פרסום מופיע בדרך כלל בשלוש הקבוצות. שלושה אותות ממוזגים טרנזיטיבית (union-find):

| אות | למה זה עובד |
|---|---|
| **MD5 של המדיה** | אותה תמונה מועברת בייט-בייט בין הקבוצות — האות החזק ביותר |
| **טלפון + דמיון טקסט** | טלפון לבדו מזהה *תורמת*, לא פרסום — לכן נדרש גם דמיון טקסט (Jaccard ≥0.4) |
| **דמיון טקסט** | תופס שכתובים ושגיאות הקלדה |

**שומר חשוב:** האש משמש לזיהוי רק אם הוא מופיע לכל היותר פעם אחת בכל קבוצה. תמונות "בוילרפלייט" (נהלי הקבוצה) מפורסמות עשרות פעמים והיו מאחדות פרסומים לא-קשורים.

## מה נחשב "מסירה"

לא כל בלוק הוא פרסום. הצ'אטים מכילים גם תיאום, נהלים וברכות. **האות המרכזי הוא מדיה** — חפצים מצטלמים.
בלוק ללא מדיה נספר רק אם זוהו בו גם פריט וגם עיר, והוא אינו הודעת "נתפס".

הודעות נהלים מזוהות בנפרד: הן **לא** נכרות לפריטים (הן מונות סוגי חפצים לדוגמה ויצרו "פריטי רפאים").

## עברית וערבית

- **נורמליזציה**: `ة→ه`, `ى→ي`, `أإآ→ا`, הסרת ניקוד. בלעדיה כשליש מההתאמות התפספסו.
- **גבולות מילה**: מותרות תחיליות (`و`, `ال`, `ب`…) וסופיות (`ها`, `هن`, `ات`…), אחרת `واحذية` ו-`كراسيها` לא נתפסים — אבל `مهد` לא ייתפס בתוך השם `مهدي`.
- **מונחים דו-משמעיים הוסרו**: `مرتبة` (מזרן / "מסודר") ו-`مهد` (עריסה / שם פרטי).

## קבצי פלט

| קובץ | תוכן |
|---|---|
| `wa-blocks.json` | בלוקים אחרי איחוד כפילויות + מקורות המיזוג (לביקורת) |
| `wa-listings.json` | אחרי חילוץ עיר ופריטים |
| `wa-items.json` | אחרי העשרה במשקלים — הקובץ שטבלת הביקורת קוראת |
| `kpis / categories / weights / items-timeline` | במבנה זהה לקבצים החיים |
| `volume.json` | נפח לפי עיר: היסטוריה + חדש |
| `wa-unresolved.json` | פרסומים שלא זוהה בהם פריט — מועמדים לזיהוי מתמונה |

## זיהוי מהתמונות (vision)

כ-38% מהפרסומים היו תמונה + עיר/טלפון בלבד, בלי תיאור של החפץ. הפער נסגר בעזרת מעבר חזותי:

1. `make-sheets.js` בוחר תמונה מייצגת לכל פרסום לא-מזוהה → `data/whatsapp/vision-todo.json`
2. `make_sheets.py` בונה **גיליונות מגע** — רשת 4×3 של תמונות ממוספרות (36 גיליונות ל-431 פרסומים), כך שאפשר לזהות תריסר בכל פעם במקום אחת-אחת
3. התוצאות נשמרות ב-`build/whatsapp/vision-results.json` ומשולבות אוטומטית ב-`extract.js`

```bash
node build/whatsapp/make-sheets.js
python3 build/whatsapp/make_sheets.py /tmp/wa-sheets
```

התוצאה: זיהוי הפריטים עלה מ-62% ל-**98%**, מספר הפריטים מ-1,653 ל-2,703, והמשקל מ-30.9 ל-46.4 טון. בנוסף זוהו 37 פרסומים שאינם חפץ כלל (גרפיקות קידום, חתולים לאימוץ, תמונות קבוצתיות) והוסרו מהספירה.

בטבלת הביקורת כל פריט שזוהה מתמונה מסומן **"מהתמונה"** כדי שאפשר יהיה לבדוק אותו בנפרד.

## יחידות מידה — הנקודה העדינה ביותר

הקטלוג באיירטייבל מערבב **שני סוגי יחידות**, וזה מקור לטעויות משקל חמורות:

| סוג | דוגמה | משמעות המשקל |
|---|---|---|
| **פריט בודד** | `מקרר` 80 ק"ג | מקרר אחד |
| **מכל** | `שקית נעלים` 8 ק"ג | **שקית שלמה** של נעליים — לא זוג! |

הזיהוי מהתמונות סופר **פריטים בודדים** (25 זוגות נעליים), ולכפול אותם במשקל המכל נתן 200 ק"ג במקום 20.
`units.json` מגדיר לכל שורת-מכל את משקל **הפריט הבודד** בתוכה, וההמרה נעשית ב-`build-exp.js`.
בטבלת הביקורת מוצגות שתי הקריאות: `שקית נעלים ×3 (25 זוג נעליים)`.

## כמויות מטקסט — מלכודת המידות

`quantityNear` קרא **מידות בגדים כמויות**: `عبايات 48 42 46` הפך ל-46 יחידות = 552 ק"ג.
התיקון: מילת מידה סמוכה (`نمره`, `رقم`, `مقاس`, `جيل`, `عمر`, `صف`) פוסלת את המספר, ותקרה של 12 יחידות לכמות מטקסט.

## סיווג — מונחי ניב

`شنطة/شنتات` בניב הבדואי הוא **תיק בית ספר**, לא מזוודה. ההקשרים חד-משמעיים ("שנתאת לגן ולכיתה א׳").
מיפוי שגוי ל`מזוודה` (5 ק"ג) במקום `תיק בית ספר` (1 ק"ג) ניפח 49 פריטים. `مزودة`/`حقيبة سفر` בלבד הן מזוודה.

בנוסף, 14 שורות בקטלוג חסרות קטגוריה ונפלו ל"אחר" — `categories-fallback.json` משלים אותן **לתצוגה בלבד**.

## שני הטאבים בדף הבית

- **מסלולי מסירה** — מפת הזרימה המקורית, ללא שינוי. מבוססת על `flows.json` (Airtable בלבד).
- **כמויות לפי יישוב** — עיגול לכל מועצה, שטחו יחסי למספר המסירות, פופאפ עם מסירות/חפצים/משקל.

צריך שתי מפות ולא אחת: בוואטסאפ נרשם רק **מוצא** החפץ, אין יעד לצייר אליו קו — ולכן
הנפח שלו לא נראה על מפת המסלולים למרות שהוא חלק מאותם סכומים מאוחדים.

מפת הנפח ב-`exp.html` (ביקורת) בנויה על אותו עיקרון.
כל מועצה היא עיגול ש**שטחו** יחסי למדד הנבחר (רדיוס לפי שורש), בצבע הקבוע של המועצה מ-`COUNCIL_COLORS`.

- **גודל העיגול:** מספר המסירות (שטח יחסי, רדיוס לפי שורש).
- **מקור:** תמונה מאוחדת אחת — היסטוריה (Airtable) + וואטסאפ מחוברים, בלי הפרדה.
- **פופאפ:** מסירות · חפצים · משקל.
- יישובים ללא קואורדינטות (למשל `אחר`) מדווחים בשורת ההערה מעל המפה במקום להיעלם בשקט.

## מגבלות ידועות

- **25 פרסומים (2%)** נותרו ללא זיהוי — וידאו בלבד או תמונה לא קריאה.
- **אין עיר יעד** בוואטסאפ — רק מוצא. קווי הזרימה ההיסטוריים נשארים כפי שהם.
- **אין "נהנים"** — ה-KPI הזה היסטורי בלבד.
- **"מסירה" = פרסום**, בעוד שב-Airtable נרשמו מסירות שאושרו. השוואה בין התקופות דורשת זהירות.
